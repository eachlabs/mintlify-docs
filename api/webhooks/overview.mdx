## What Are Webhooks?

Instead of polling for prediction results, you can provide a `webhook_url` when creating a prediction. each::labs will POST the result to your URL when the prediction completes.

<Note>
  Currently, webhooks are only supported for Workflows V2. Support for other services is being expanded.
</Note>

## How It Works

<Steps>
  <Step title="Provide a webhook URL">
    Include `webhook_url` when creating a prediction, plus `webhook_secret` if you want deliveries signed.
  </Step>
  <Step title="Prediction runs">
    The model processes your input asynchronously.
  </Step>
  <Step title="Result delivered">
    When complete, each::labs POSTs the result to your webhook URL.
  </Step>
</Steps>

## Setting Up Webhooks

```bash
curl -X POST https://api.eachlabs.ai/v1/prediction \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d '{
    "model": "flux-1-1-pro",
    "version": "1.0.0",
    "input": {"prompt": "A mountain landscape"},
    "webhook_url": "https://your-app.com/webhooks/prediction",
    "webhook_secret": "whsec_your_secret_key"
  }'
```

When you supply `webhook_secret`, each delivery is signed with HMAC-SHA256 and carries `X-Webhook-Signature` and `X-Webhook-Timestamp` headers. See [Verifying Webhook Signatures](/api/webhooks/verifying-signatures). Omit the secret and deliveries are still sent, just unsigned.

## Retry Behavior

Deliveries are attempted up to 3 times in total: the initial attempt plus 2 retries, spaced roughly 10 seconds apart. Every attempt of one delivery carries the same signature and timestamp. You can track delivery attempts using the [Get Webhook](/api/webhooks/get-webhook) endpoint.

### Delivery Attempt Statuses

| Status | Description |
|--------|-------------|
| `PENDING` | Delivery is queued |
| `SUCCESS` | Delivered successfully (2xx response) |
| `FAILED` | Delivery failed (timeout, non-2xx, or connection error) |

## Redelivery

If a delivery failed, or your endpoint was down when it arrived, you can send the same payload again. Open the webhook on the **Webhooks** page in the dashboard and choose **Redeliver**.

A redelivery is a fresh delivery of the original payload:

- The request body is byte-for-byte the original.
- It carries `X-Webhook-Redelivery: true`. An ordinary delivery does not send this header at all, so your endpoint can tell the two apart. The header is set when the request is sent and cannot be supplied through your own webhook headers.
- A signed webhook is signed again at send time, so its signature and timestamp differ from the original delivery. See [Redeliveries are signed again](/api/webhooks/verifying-signatures#redeliveries-are-signed-again).
- It is sent once. The retry policy above covers the original delivery, not a redelivery. To try again after a redelivery fails, redeliver again.
- The attempt is recorded alongside the original attempts and appears in [Get Webhook](/api/webhooks/get-webhook). The response does not mark which attempt was a redelivery — only the delivered request carries the header.

Because a redelivery repeats a payload your endpoint may already have processed, handle deliveries idempotently. Key on `execution_id` rather than assuming every request is new.

**Redelivery** is offered only when it would succeed. It is unavailable while a delivery is still in flight, for a short cooldown after a redelivery, and once the stored payload has been erased.
