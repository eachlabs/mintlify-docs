## Overview

A model step can name a fallback model. If the primary model fails (an outage, a rate limit, a
refusal), the fallback runs with its own parameters, and the workflow continues with its result.

## How it works

1. The primary model runs with the step's `params`.
2. If it fails, the fallback model runs with the fallback's `params`.
3. If both fail, the step fails.

Later steps don't need to know which model answered: `$.<step_id>.primary` is the fallback's
result when the fallback ran.

## Configuration

Add a `fallback` object to a model step. Map the inputs again in the fallback's `params`, because
the second model often takes different parameter names:

```json
{
  "id": "restyle",
  "type": "model",
  "model": "nano-banana-2-edit",
  "params": {
    "prompt": "Restyle this photo as $.inputs.style. Keep the person's face unchanged.",
    "image_urls": ["$.inputs.photo"],
    "aspect_ratio": "9:16"
  },
  "fallback": {
    "enabled": true,
    "model": "gpt-image-v2-edit",
    "params": {
      "prompt": "Restyle this photo as $.inputs.style. Keep the person's face unchanged.",
      "image_urls": ["$.inputs.photo"],
      "image_size": "1024x1536"
    }
  }
}
```

The full workflow is example 2 on the [overview](/workflows/overview).

## Fallback properties

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `enabled` | boolean | `true` | Turn the fallback on or off |
| `model` | string | `-` | Fallback model slug |
| `params` | object | `-` | Parameters for the fallback model; supports [`$.` references](/workflows/concepts/parameter-references) |

## Detecting fallback usage

When a step has a fallback, the execution's `step_outputs` has an extra entry `<step_id>_fallback`:

```json
{
  "restyle": {
    "step_id": "restyle",
    "status": "failed",
    "error": "provider rate limit"
  },
  "restyle_fallback": {
    "step_id": "restyle_fallback",
    "status": "completed",
    "primary": "https://cdn-us.eachlabs.ai/uploads/7c1e.png",
    "fallback": { "fallback_from_step": "restyle", "reason": "primary_failed" }
  }
}
```

`fallback.reason` is `primary_failed` when the fallback ran and `not_triggered` when the primary
model succeeded.

## Best practices

- Pick a fallback that returns the same kind of output (an image URL for an image step).
- Use fallbacks on steps your product depends on, especially video and LLM steps.
- Watch `primary_failed` in your results to spot a primary model that fails often.
- Check the fallback model's price; it may differ from the primary's.
